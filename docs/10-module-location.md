# 10. 자리 이력 모듈 (`location`)

## 1. 목표와 범위

- **사용자 질문**: "이 자리(건물의 이 층)에 전에 어떤 가게들이 있었고, 이런 이력의 자리에 새로 연 가게들은 실제로 어떻게 됐나?"
- **표시 단위**: 층키 = `(pnu, floor)` (ADR-015, ADR-016)
- **데이터**: 서울, 식품 3종 인허가 (docs/03 D1)
- **하지 않는 것**: 위험 점수, 매출·상권 추정, 평가적 표현 (ADR-005, docs/60 §3)

### 1.1 범위에서 빼는 기록 (T-016에서 정함, 2026-10-13)

| 대상 | 처리 | 근거 |
|---|---|---|
| 주소가 서울 밖인 행 (`지번주소`·`도로명주소` 둘 다 `서울특별시`로 시작하지 않음) | 정규화에서 제외, `license_record`에 넣지 않는다. 수는 `validation.normalize.non_seoul_excluded` | 2026-10 파일: 일반음식점 14, 휴게음식점 9, 제과점영업 2 |
| 고정된 자리가 없는 업태: `업태구분명`이 `푸드트럭`, `이동조리` | `license_record.no_fixed_place = true`. 기록은 남기되 **자리 이력(§7.1)·과거 폐업 횟수·통계(§7.2)에서 제외**. 수는 `validation.normalize.no_fixed_place` | 주소가 영업 장소가 아니라 차량·행사장이다. 푸드트럭 1,254건(층 표기 10%, 꼬리에 `여의도한강공원 물빛광장(차량번호)` 등), 이동조리 101건(꼬리의 44%가 `차량번호NN`). 비교: 한식은 층 표기 48% |
| 편의점 (`업태구분명 = '편의점'`, 13,291건) | **자리 이력에는 표시**한다. 기준율 통계(§7.2 코호트)에서는 기본 제외. `biz_category`를 그대로 보존해 T-019가 포함/제외 민감도를 비교한다 | 음식점과 폐업 양상이 다른 업태가 휴게음식점 인허가에 섞여 있다 |

- `출장조리`(430건)는 빼지 않는다. 조리장 주소가 있고 층 표기 비율(54%)이 한식과 비슷하다
- `업태구분명` 원문 값 전체 목록과 건수는 `data/README.md`. 새 값이 생겨도 실패로 보지 않는다(값은 그대로 `biz_category`에 둔다)

## 2. PNU 생성

PNU(필지고유번호, 19자리) = `법정동코드(10)` + `산 여부(1: 일반 '1', 산 '2')` + `본번(4, 0 채움)` + `부번(4, 0 채움)`

### 2.1 인허가 기록의 지번주소에서

```
정규식 (공백 정규화 후 적용, W0에서 서울 99.9% 파싱 성공):
^서울특별시\s+(?P<sigungu>\S+구)\s+(?P<dong>\S+)\s+(?P<san>산\s*)?(?P<main>\d+)(?:-(?P<sub>\d+))?(?P<tail>.*)$
```
- `dong`은 아무 토큰이나 받고, 유효성은 `legal_dong` 조회로 판정한다
- `법정동코드` = `legal_dong.full_name = '서울특별시 {sigungu} {dong}'` 조회. 실패 시 `pnu=NULL`, 실패 사유 카운트
- 제공 파일은 현행 코드만. 폐지 동명 때문에 조회에 실패한 건수를 리포트에 따로 남기고, 전체 실패율이 0.5% 안이면 폐지 코드는 적재하지 않는다 (docs/03 D3). 아래 폐지 코드 규칙과 `legal_dong.abolished`는 폐지 코드 파일을 나중에 넣을 때를 위해 그대로 둔다
- 같은 이름에 코드가 여러 개일 때 (T-011에서 확정):
  - 현행 코드가 1개면 폐지 코드가 함께 있어도 **현행 코드**를 쓴다. 사용자 주소 검색(§2.2)은 도로명주소 API가 현행 코드를 주므로, 폐지 코드로 만든 PNU는 검색 결과와 맞지 않는다
  - 현행 코드가 없고 폐지 코드만 1개면 폐지 코드로 PNU를 만든다. 실패가 아니며 실패율에 넣지 않는다. 건수는 따로 세어 리포트에 적는다 (`abolished_only`)
  - 현행 코드가 2개 이상이면 PNU를 만들지 않는다. 실패 사유 `ambiguous`
  - 현행 코드가 없고 폐지 코드만 2개 이상이어도 고를 근거가 없으므로 `ambiguous`
- 실패 사유: `regex_mismatch`(정규식 불일치), `dong_not_found`(이름이 `legal_dong`에 없음), `ambiguous`. 뒤 둘이 정의의 "`legal_dong` 조회 실패"다
- `main`·`sub`가 4자리를 넘으면 PNU 19자리에 담을 수 없으므로 `regex_mismatch`로 센다
- `sub`가 없거나 `0`이면 `0000`
- `tail`은 층·호 파싱에 사용

| 입력 | 기대 |
|---|---|
| `서울특별시 광진구 화양동 47-1 ` | 화양동 코드 + `1` + `0047` + `0001` |
| `서울특별시 광진구 광장동 110-0` | 부번 `0000` |
| `서울특별시 광진구 광장동 산 21` | 산 여부 `2`, 본번 `0021` |
| `서울특별시 중구 을지로3가 296-1` | 동 이름 `을지로3가` |
| `서울특별시 종로구 종로1가 24` | 동 이름 `종로1가` |
| `서울특별시 광진구 자양동 227-342 롯데백화점스타시티점 지하1층` | PNU 정상, `tail` = `롯데백화점스타시티점 지하1층` |
| `서울특별시 광진구 구의동 631-1 프라임 상가 1층 124, 134,135` | `tail` = `프라임 상가 1층 124, 134,135` |
| `서울특별시  광진구   군자동 49-19` (공백 여러 개) | 공백 정규화 후 정상 |

> **PNU 생성 실패율** = (지번 정규식 불일치 + `legal_dong` 조회 실패) ÷ 서울 필터를 통과한 전체 기록. 기준 **< 0.5%** (T-011 수용 기준, DV6, Gate 1 공통). 실패 사례 상위 20개를 리포트에 남긴다.

### 2.2 사용자 주소 검색 결과에서 (도로명주소 API)

`pnu = admCd + ('2' if mtYn == '1' else '1') + lnbrMnnm.zfill(4) + lnbrSlno.zfill(4)` 🔎 T-021에서 응답 필드 확인

## 3. 층 파서

입력: `tail`(지번주소 꼬리), `road_detail`(도로명주소 첫 쉼표 뒤 문자열)
순서: `tail`에서 먼저 찾고, 없으면 `road_detail`. 둘 다 있고 값이 다르면 `tail` 값을 쓰고 `floor_conflict` 지표를 1 증가.

**규칙 (위에서부터 첫 매치)**

| 우선 | 패턴 (대소문자 무시) | 결과 |
|---|---|---|
| 1 | `지하\s*(\d+)\s*층` | `B{n}` |
| 2 | `지하층` 또는 `지층` | `B1` |
| 3 | `(?<![가-힣A-Za-z0-9])(?:제\s*)?지\s*(\d+)\s*층` (앞 글자가 한글·영문·숫자가 아닌 "지N층"·"제지N층" — 지하 N층의 줄임 표기) | `B{n}` |
| 4 | `(?<![A-Za-z])B\s*(\d{1,2})(?!\d)(?!\s*호)(?:\s*층|F\b)?` (B 뒤 1~2자리, 호수 아님) | `B{n}` |
| 5 | `(\d+)\s*[~,\-]\s*(\d+)\s*층` (범위·복수 층) | 둘 중 낮은 층 |
| 6 | `(?:지상\s*|제\s*)?(\d+)\s*층` | `{n}` |
| 7 | `(\d+)\s*F\b` | `{n}` |
| 8 | `옥탑` 또는 `옥상` | `RF` |

- 결과가 지상 `0` 또는 100 이상, 지하 `B0` 또는 `B10` 이상 → `NULL` (오입력)
- 위 규칙과 아래 표는 설계 시점에 Python `re`로 전부 통과 확인함(2026-10-12)
- 규칙 3은 T-012에서 추가(2026-10-12). 근거: 식품 3종 원천 파일(704,116행)에서 단독 "지N층" 6,318번 중 반대쪽 주소 문자열이 층을 따로 적은 110번 가운데 108번이 같은 숫자의 지하층(지상 1층 2번). "제지N층"은 627번 중 교차 확인 가능한 3번이 모두 같은 숫자의 지하층
- "제지N층"을 규칙 3에 넣은 논리와 한계: "제"는 규칙 6이 `제1층`처럼 서수 접두로 읽는 글자라 "제지N층"은 "제 + 지N층", 곧 "지N층"과 같은 표기로 보고 그 근거(110번 중 108번, 98%)를 함께 쓴다. 보조 근거: 627번 중 388번은 같은 문자열에 `제비201호`·`B…`·`지하` 같은 지하 표시가 함께 있다. **한계: "제지N층" 자체의 교차 확인은 3번뿐(3/3, 95% Wilson 하한 약 44%)이라 이 수치만으로는 근거가 얇다**
- 규칙 3이 읽지 않는 것: 건물명에 붙여 쓴 `OO빌딩지1층`(앞 글자가 한글·영문·숫자). `외3필지 3층`, `2단지 1층`, `번지 2층`, `빌리지 1층`과 글자만으로 구분할 수 없어 지상층(규칙 6)으로 읽는다 — 알려진 한계(docs/80 제안 티켓)
- 정규화 값 정렬 순서: `B9 … B1, 1, 2, …, RF`

## 4. 호 파서

입력: `tail`(지번주소 꼬리), `road_detail`(도로명주소 첫 쉼표 뒤 문자열) — 층 파서와 같다
순서: `tail`에서 먼저 찾고, 없으면 `road_detail`. 둘 다 있고 목록이 다르면 `tail` 목록을 쓰고 `ho_conflict` 지표를 1 증가. 두 목록을 합치지 않는다(한쪽의 오타가 섞인다 — 예: `1012호` / `102호`).

**규칙 (문자열 하나에서 모든 매치를 모은다)**

| 규칙 | 패턴 | 결과 |
|---|---|---|
| 1 | `(?<!\d)(?<!\d-)(NUM(?:\s*[,.]\s*NUM)*)\s*호(?![선동점관])`, 여기서 `NUM` = `(?:\d{3,}\s*\.\s*\d(?!\d)\|\d+(?:-\d+\|-[A-Za-z])?)` (`호`로 끝나는 번호, 또는 쉼표·마침표로 구분된 번호 목록 전체) | 목록의 번호 전부 |
| 2 | `층\s*(\d{3,4}(?:\s*,\s*\d{3,4})+)(?!\d)` (층 바로 뒤, `호` 글자 없이 쉼표로 구분된 3~4자리 숫자 2개 이상) | 목록의 번호 전부 |

- 번호는 `N` 또는 가지번호 `N-M`(숫자)·`N-A`(영문 한 글자, 대문자로 통일: `132-a호` → `'132-A'`). **가지번호는 문자열 그대로 한 원소**(`201-5호` → `'201-5'`). `'5'`로 읽으면 같은 층의 `101-5호`와 `102-5호`가 같은 호로 묶여 §6 미갱신 의심이 잘못 뜬다. §6·§7은 원소 문자열이 같을 때만 같은 호로 보므로 `'201-5'`와 `'201'`은 다른 호다
- 마침표는 목록 구분자다(`20.21호` → `'20'`, `'21'`). 단, **앞 숫자가 세 자리 이상이고 마침표 뒤 숫자가 한 자리이면 가지번호**로 읽는다(`104.1호` → `'104-1'`). 목록으로 읽으면 `'1'`이라는 틀린 값이 들어가 같은 층의 1호와 묶인다
- `호` 바로 뒤 글자가 `선`·`동`·`점`·`관`이면 호수가 아니다(`2호선`, `3호동`, `1호점`, `2호관`). `호실`은 호수로 읽는다(`113호실` → `'113'`)
- 번호 앞의 영문·한글 접두는 버린다(`B101호`·`제비201호` → `'101'`·`'201'`, `가동 101호` → `'101'` — 동 구분은 MVP에서 무시)
- 정규화: 본번·가지번 각각 앞의 0 제거(`0101` → `101`, `3-01` → `3-1`), 본번이 0이면 버림(`0호` — 층 파서의 `0층`과 같은 오입력), 중복 제거, **(본번, 가지번) 오름차순** — 본번은 숫자순, 같은 본번 안에서는 가지번 없는 것 → 숫자 가지번(숫자순) → 영문 가지번(알파벳순): `101, 101-1, 101-2, 101-A, 101-B, 102, 1002`
- 호를 읽지 못하면 빈 목록 `[]`
- 규칙 1의 제외 글자·쉼표·마침표 목록·가지번호와 입력 순서는 T-013에서 정함(2026-10-13). 근거: 식품 3종 원천 파일(704,116행, 2026-10-08·10-12 파일)에서 센 값
  - 호가 적힌 곳: `road_detail`에만 67,721행, `tail`에만 24,973행, 양쪽 46,724행(이 중 목록이 서로 다른 것 1,029행) — 규칙을 넓히기 전 `(\d+)\s*호`로 센 값
  - `숫자+호` 바로 뒤 글자(둘 중 한 문자열에라도 있는 행 수 / 나온 횟수): `호선` 730행 / 1,192번, `호동` 146행 / 184번, `호점` 36행 / 49번, `호관` 7행 / 10번, `호실` 13행 / 16번. 일반음식점 파일만으로는 `호동` 126행, `호선` 50행, `호점` 12행, `호실` 12행, `호관` 1행
  - 쉼표 목록 뒤 `호`(`101,102호`) 10,556행, 가지번호(`201-5호`) 7,299행, 범위(`214~215호`) 1,773행
  - 영문 가지번(`132-A호`) 181행, 마침표가 든 번호 목록(`20.21호`) 307행. 이 중 마침표 가지번호 규칙(`104.1호` 꼴)에 걸리는 것은 **9행**(서로 다른 문자열 10개: `104.1호` 2, `103.4호` 3, `401.2호`, `201.2호`, `105.7호`, `105 . 6호`, `102.3.201호`)

## 5. 폐업 처리 급증일 탐지 (ADR-020, 옛 이름: 행정 일괄 폐업일)

```
대상: status='closed' AND closed_on IS NOT NULL
c(j, d) = 관할 j(개방자치단체코드), 날짜 d의 폐업 건수 (식품 3종 합산)
m(j)    = 관할 j에서 폐업이 1건 이상 있었던 날들의 c(j, d) 중앙값
bulk(j, d) = c(j, d) >= 30 AND c(j, d) >= 10 * m(j)
```
- 해당 (j, d)의 기록 전체에 `bulk_closure=true`
- 탐지된 (j, d)마다 관할 이름·건수·중앙값을 `closure_surge_day`에 저장한다(docs/04). 화면의 "폐업 처리 몰린 날" 설명(docs/40 §4.4)이 이 값을 쓴다. 관할 이름은 원천에 없으므로(코드만 있다) 그 관할 기록의 지번주소(없으면 도로명주소)에 가장 많이 나온 시군구 이름으로 정한다
- 계산 대상은 `license_record`에 들어가는 기록 전체(§1.1의 서울 밖 행은 빠지고, `no_fixed_place` 기록은 포함 — 관할이 처리한 폐업 건수라는 사실을 센다)
- 지표: 탐지 날짜 수, 기록 수를 `data_snapshot.validation`에 기록
- 이 규칙이 말하는 것은 **"그날 그 관할에서 평소보다 훨씬 많은 폐업이 처리됐다"는 사실**뿐이다. "행정 일괄 정리"라는 해석은 검증하지 못했다(ADR-020 측정 기록). 화면 문구도 사실만 쓴다(docs/40 §4.4)
- 측정(T-015): `python -m jobs.measure_bulk_closure` → `reports/bulk_closure.md`. 식품 3종 원천(704,141행)에서 탐지 (관할, 날짜) 495개(서로 다른 날짜 481일), 기록 45,850건. W0 방식과의 일치와 타당성 측정 결과는 ADR-020
- 통계에서의 제외: `method_version='w0'` 재현 모드는 W0 정의(일반음식점, 서울 전체 하루 100건 이상)를 그대로 쓴다. 새 버전의 **기본 설정은 이 규칙으로 제외**한다(§7.2, 2026-10-13 결정). 제외 없음 / W0 정의로 바꾼 결과는 민감도 분석으로 함께 낸다(§7.3 `sensitivity.bulk_exclusion`)

## 6. 미갱신 의심 (ADR-023)

영업 중으로 남아 있는 기록 A와, 같은 층키에서 **A보다 나중에 개업한** 다른 기록 B의 쌍을 본다.

- 대상: A·B 모두 `pnu`·`floor`·`opened_on`이 있고 `no_fixed_place = false`. A는 `status='open'`, B는 상태와 상관없다(이미 폐업했어도 된다). `B.opened_on > A.opened_on`
- **같은 가게로 보이는 쌍은 뺀다.** 식품 3종을 합쳤기 때문에 한 가게가 같은 호에 일반음식점과 휴게음식점(또는 제과점) 기록을 함께 가질 수 있고, 같은 종류 안에서도 다시 신고한 기록이 있다. 사업장명을 정규화(`(주)`·`㈜`·`주식회사` 제거 → 공백·문장부호 제거 → 영문 소문자)한 뒤 **두 이름이 같거나, 한쪽이 다른 쪽을 포함하면**(둘 다 2자 이상) 같은 가게로 본다
  - 글자 유사도는 쓰지 않는다. 지점 이름이 같은 다른 가게(`OO 동대문디자인플라자점`끼리)가 높게 나온다
- **여러 사업자가 함께 쓰는 호는 같은 호 근거에서 뺀다.** 한 층키에서 어떤 호 번호를 `ho_list`에 가진 **영업 중 기록이 3건 이상**이면 그 호를 공유 공간(공유주방, 푸드코트의 한 호 등)으로 보고, A와 B가 그 호로만 겹치는 쌍은 같은 호 근거로 세지 않는다. 세는 대상은 위 "대상"과 같은 기록이다
  - 기준: 화면에 보이는 부정적인 표시이므로 **틀린 배지보다 놓친 배지가 낫다**. 영업 중 기록이 여럿인 호에서는 "나중 신고"가 폐업 신고 지연이 아니라 동시 영업일 가능성이 높다
  - 같은 면적 근거(`stale_area_match`)에는 이 규칙을 적용하지 않는다(화면에 내지 않는다)
  - 공유 공간으로 보아 표시가 빠진 기록 수는 리포트에 "공유 공간 추정으로 제외"로 따로 적는다
- 남은 쌍의 근거를 나눠 저장한다

  | 근거 | 조건 | 컬럼 | 쓰는 곳 |
  |---|---|---|---|
  | 같은 호 | A와 B의 `ho_list`가 하나 이상 겹침 | `stale_suspect` | 화면 배지·알림(`stale_suspect_present`)·API, 통계 민감도 분석 |
  | 같은 면적 | 둘 다 면적이 0보다 크고, 차이가 큰 쪽 면적의 1% 이하 | `stale_area_match` | **통계 민감도 분석에만.** 화면·API에 내지 않는다 |

  - 두 컬럼은 서로 독립이다(둘 다 참일 수 있다)
  - 면적 근거를 화면에 쓰지 않는 이유: 우연한 겹침이 많다. T-015 측정에서 같은 조건의 면적 ±1% 겹침이 일반 폐업에서도 8.05% 나왔다(ADR-020 측정 기록)
- 화면(docs/40 §4.4): `stale_suspect = true`인 A 옆에 배지와 설명 "같은 호수로 나중에 다른 가게가 영업 신고를 했어요. 이 가게의 폐업 신고가 늦어졌을 수 있어요." 해석("폐업한 가게")이 아니라 사실과 가능성만 말한다
- 통계 계산에는 쓰지 않는다. 민감도 분석(§7.3 `sensitivity.exclude_stale`)에서 같은 호 근거만 뺀 결과와, 같은 호 또는 같은 면적을 뺀 결과를 함께 본다
- 실행: `python -m jobs.flag_stale_suspects` — 정규화(`jobs.normalize_licenses`) 뒤에 실행한다. 두 컬럼을 전체 기록에 다시 쓰고(같은 입력이면 같은 결과), 근거별 건수와 같은 가게로 보아 뺀 건수를 `reports/stale_suspect.md`에 적는다
- 측정(T-017, 2026-10 세 파일, `reports/stale_suspect.md`): 대상 132,191건
  - 같은 호 근거 **1,850건**(1.40%), 같은 면적 근거 8,757건(6.62%) — 같은 호만 1,060, 둘 다 790, 면적만 7,967
  - 같은 가게로 보아 뺀 쌍: 같은 호 5,525쌍 중 149쌍(표시가 사라진 기록 108건), 같은 면적 31,503쌍 중 213쌍(153건)
  - 공유 공간 추정으로 제외: 공유 공간으로 본 (층키, 호) 229곳. 같은 호 근거 2,380건 중 **530건(22.27%)**이 빠졌다
  - 남은 1,850건에서 근거가 된 호의 영업 중 기록 수(자신 포함): 1건 952(51.46% — 나중에 연 가게는 이미 폐업), 정확히 2건 898(48.54%)
- 알려진 한계
  - 공유 공간 규칙을 넣기 전에는 같은 호 근거 기록이 10건 이상 몰린 층키가 27곳(430건)이었다. 규칙 뒤에는 20곳이 10건 아래로 내려가고 **7곳(89건)이 남는다.** 남은 7곳은 한 호에 몰린 것이 아니라 여러 호에 흩어져 있다(층키별 기록 19·13·13·12·12·10·10건이 서로 다른 호 33·14·21·13·16·13·10개에 걸침 — 호가 많은 큰 층)
  - 영업 중 기록이 2건인 호를 두 사업자가 나눠 쓰는 경우는 여전히 잡힌다(3건 이상만 공유 공간으로 본다)
  - 호 표기가 없는 공유 공간은 같은 호 근거에 애초에 잡히지 않고, 면적 근거(`stale_area_match`)에는 이 규칙을 적용하지 않는다

## 7. 이력과 통계

### 7.1 층 이력 (화면용)

정렬: `opened_on` 오름차순. 각 항목:
`{record_id, name, biz_category, license_type, opened_on, closed_on, status, tenure_days, ho_list, bulk_closure, stale_suspect}`
- `tenure_days` = (`closed_on` 또는 기준일) − `opened_on`
- 같은 `ho_list` 원소를 공유하는 기록끼리는 화면에서 "같은 호수로 신고된 기록"으로 묶어 색을 맞춘다 (연결선 표시)
- `has_concurrent` = 이력 중 영업 기간이 30일 넘게 겹치는 쌍 존재 → "이 층에는 여러 점포가 함께 있을 수 있어요"
- `record_suppression`에 있는 기록과 `no_fixed_place = true`인 기록은 제외 (§1.1). 편의점은 이력에 보이고 `biz_category`로 구분된다

**빌드 (`jobs.build_history`, T-018)** — 정규화·미갱신 표시 뒤에 실행한다. `parcel`·`floor_summary`·`record_prior`를 전부 다시 만든다(같은 입력이면 같은 결과)

- 기준일: 인자 `--as-of`. 주지 않으면 `validated` 스냅샷의 `source_updated_max` 중 가장 이른 날짜(Asia/Seoul) — 통계 기준일(T-019)·`location_snapshot`과 같은 날짜
- 이력에 보이는 기록 `H` = `pnu`가 있고 `no_fixed_place = false`이며 `record_suppression`에 없는 기록
- `parcel`: `H`에 기록이 1건 이상 있는 필지마다 1행(층 정보가 하나도 없으면 `floors = {}`)
  - `jibun_label` = `legal_dong.full_name` + (산이면 ` 산`) + ` 본번`(부번이 0이 아니면 `-부번`) — PNU에서 만든다
  - `road_addr` = 도로명주소가 있는 기록 중 가장 최근에 개업한 기록의 도로명주소에서 첫 쉼표 앞부분. `geom` = 좌표가 있는 기록 중 가장 최근에 개업한 기록의 좌표. 개업일이 같으면 `id`가 큰 쪽, 개업일이 없는 기록은 맨 뒤
  - `floors` = `H`에서 층이 있는 기록의 층, §3의 정렬 순서. `record_count` = `H`의 그 필지 기록 수(층 없는 기록 포함)
- `floor_summary`: `H`에서 층이 있는 기록의 층키마다 1행
  - `record_count`, `records_since_2005`(`opened_on ≥ 2005-01-01`), `open_now_count`(`status='open'`)
  - `median_closed_tenure_days` = `status='closed'`이고 개업일·폐업일이 있으며 `bulk_closure = false`인 기록의 `closed_on − opened_on` 중앙값(짝수 개면 가운데 두 값의 평균, 0.5는 올림). 해당 기록이 없으면 `NULL`
  - `has_concurrent`: 기록의 영업 기간 = `[opened_on, closed_on]`, 영업 중이면 `[opened_on, 기준일]`. 두 기록의 겹침 = `min(끝) − max(시작)`일. **30일을 넘는**(31일 이상) 쌍이 있으면 참. 개업일이 없거나, 폐업인데 폐업일이 없는 기록은 기간을 알 수 없으므로 이 판정에서 뺀다
- `record_prior`: §7.2의 `F`에서 개업일이 있는 기록마다 1행 (숨김 기록도 포함 — 통계용 값이다)
- 측정(T-018, 2026-10 세 파일, 기준일 2026-10-07): 필지 157,898곳(층 정보가 하나도 없는 필지 50,066곳), 층키 148,604곳(동시 영업 있음 36,457곳), `record_prior` 382,601행. 급증일 폐업을 빼면 과거 폐업 횟수가 달라지는 기록은 31,248건(8.2%)이고, 그중 26,249건은 포함한 값이 4 이상인 기록이다. 빌드 약 10초(로컬)

### 7.2 과거 폐업 횟수와 기준율

**정의 (method_version `2026.10.1`)**
- 층키 기록 집합 `F(pnu, floor)` — 식품 3종, `floor IS NOT NULL`, `no_fixed_place = false` (§1.1)
- 기록 r의 과거 폐업 횟수: `prior(r) = |{ s ∈ F : s ≠ r, s.status='closed', s.closed_on < r.opened_on }|`. 같은 날 폐업·개업은 세지 않는다(`<`)
  - **두 값을 함께 저장한다**(`record_prior`): 급증일 폐업을 포함한 `prior_closures_floor`와, `s.bulk_closure = true`인 폐업을 뺀 `prior_closures_floor_ex_surge`. 계산 함수는 "세지 않을 폐업"을 인자로 받으므로 W0 정의(서울 전체 하루 100건 이상)로 뺀 값도 같은 함수로 낸다
  - **기본으로 쓰는 값은 급증일 폐업을 뺀 `prior_closures_floor_ex_surge`다** (2026-10-13 결정 — 결과를 보기 전에 정했다). 아래 정의의 "과거 폐업 횟수"는 이 값이다
- **기본 설정** (2026-10-13 결정, 결과를 보기 전에 정했다)

  | 항목 | 기본 | 뜻 |
  |---|---|---|
  | 급증일 | 새 규칙(`bulk_closure`, §5)으로 제외 | 급증일에 폐업한 기록은 코호트에서 빼고, 과거 폐업 횟수에도 세지 않는다 |
  | 편의점 | 제외 | 코호트에서만 뺀다(§1.1). `F`에는 남아 다른 기록의 과거 폐업 횟수에는 들어간다 |
  | 신고 지연(미갱신 의심, §6) | 제외 없음 | |
  | 층 미상 | 전체 | 층 미상 폐업 기록이 있는 필지도 포함 |
  | `no_fixed_place` | 제외 | `F`에 들어가지 않는다(§1.1). 바꾸는 설정은 없다 |

- 코호트: `opened_on ∈ [2005-01-01, 기준일 − 1095일]`, `pnu`·`floor` 있음, `r.bulk_closure = false`, `r.biz_category ≠ '편의점'`. 다른 설정의 결과는 §7.3 민감도
- 결과: `event(r) = r.status='closed' AND r.closed_on − r.opened_on ≤ 1095일`
- 버킷: `0, 1, 2, 3, 4+`
- 범위: 서울 전체(`scope_code='11'`)와 시군구별
- 비율과 Wilson 95% 신뢰구간:
  ```
  p̂ = events/n,  z = 1.96
  center = (p̂ + z²/(2n)) / (1 + z²/n)
  half   = z·sqrt(p̂(1−p̂)/n + z²/(4n²)) / (1 + z²/n)
  ```
- **표시 조건**: 해당 버킷 `n ≥ 200`. 시군구 버킷이 조건을 만족하면 시군구 값을 주로, 서울 값을 보조로 표시. 아니면 서울 값만

**측정 (T-019, 2026-10 세 파일, 기준일 2026-10-07, `reports/base_rates.md`)** — 기본 설정, 서울 전체. 코호트 250,131건(2005-01-01 ~ 2023-10-08 개업), 3년 내 폐업률 36.11%

| 과거 폐업 | 0 | 1 | 2 | 3 | 4+ |
|---|---|---|---|---|---|
| n | 134,162 | 46,941 | 21,262 | 10,484 | 37,282 |
| 3년 내 폐업률 | 30.93% | 35.40% | 38.11% | 39.39% | 53.61% |

- 화면이 쓰는 값은 이 표가 아니라 `base_rate` 테이블이다(서울 + 25개 시군구, 130행)
- 알려진 한계: `4+` 버킷은 기록이 많은 층에 크게 좌우된다. `4+` 37,282건 중 18,106건이 기록 50건이 넘는 층(`floor_summary.record_count > 50`)의 가게이고 그 3년 내 폐업률은 65.90%다. 기록 50건 이하인 층의 `4+`는 19.80~44.69%(층 기록 수 구간별). 인허가 종류별 `4+`는 일반음식점 44.88%, 휴게음식점 62.85%, 제과점영업 67.43%. 한 번 잰 값이고 재현 스크립트는 없다 — 층 규모별로 나누는 일과 이 숫자의 재현은 T-019b

**결론 유지 판정 기준 (2026-10-13, 결과를 보기 전에 적었다)** — 결론 = "과거 폐업이 많은 층에 새로 연 가게의 3년 내 폐업률이 더 높다". 설정 하나에서 아래 둘이 모두 참이면 그 설정에서 결론이 유지된다고 본다

- **(a)** 서울 전체에서 과거 폐업 `4+` 버킷의 3년 내 폐업률이 `0` 버킷보다 높고, **두 버킷의 Wilson 95% 신뢰구간이 겹치지 않는다**(`4+`의 하한 > `0`의 상한, 반올림 전 값으로 비교)
- **(b)** 위 로지스틱(`spec`, 층키 클러스터 표준오차)의 **과거 폐업 1회당 OR 95% 신뢰구간 하한 > 1**(`exp(β − 1.96·SE) > 1`). 적합이 수렴하지 않으면 유지되지 않은 것으로 본다

| 시간 겹침 금지 + 면적 ±25% 탐욕 연결 (호실 6개 이하 층) | **0.685** | **0.426** | **0.525** |

참고: 같은 호 연속 기록 중 면적이 **완전히 같은** 비율 47.1% → 강한 특징.

### 8.3 접근
1. 라벨 정제: 같은 호인데 30일 넘게 겹치는 쌍은 학습 라벨에서 제외(미갱신 의심)
2. 쌍 분류기: 특징 = 면적 완전 일치, |log 면적비|, 공백 일수, 겹침 일수, 업태 동일, 상호 유사도(자모 단위 Jaccard), 층 내 기록 수, 둘 다 호 정보 보유 여부
3. 클러스터링: 분류기 확률을 비용으로 한 최소 비용 체인(시간 겹침 금지 제약)
4. 분할: **시군구 단위** train 15 / val 5 / test 5 (같은 건물이 학습·평가에 섞이지 않게)
5. 지표: 쌍 정밀도·재현율·F1, B-cubed. 소형 층(≤6호실)과 전체를 따로 보고
