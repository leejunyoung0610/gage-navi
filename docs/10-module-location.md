# 10. 자리 이력 모듈 (`location`)

## 1. 목표와 범위

- **사용자 질문**: "이 자리(건물의 이 층)에 전에 어떤 가게들이 있었고, 이런 이력의 자리에 새로 연 가게들은 실제로 어떻게 됐나?"
- **표시 단위**: 층키 = `(pnu, floor)` (ADR-015, ADR-016)
- **데이터**: 서울, 식품 3종 인허가 (docs/03 D1)
- **하지 않는 것**: 위험 점수, 매출·상권 추정, 평가적 표현 (ADR-005, docs/60 §3)

## 2. PNU 생성

PNU(필지고유번호, 19자리) = `법정동코드(10)` + `산 여부(1: 일반 '1', 산 '2')` + `본번(4, 0 채움)` + `부번(4, 0 채움)`

### 2.1 인허가 기록의 지번주소에서

```
정규식 (공백 정규화 후 적용, W0에서 서울 99.9% 파싱 성공):
^서울특별시\s+(?P<sigungu>\S+구)\s+(?P<dong>\S+)\s+(?P<san>산\s*)?(?P<main>\d+)(?:-(?P<sub>\d+))?(?P<tail>.*)$
```
- `dong`은 아무 토큰이나 받고, 유효성은 `legal_dong` 조회로 판정한다
- `법정동코드` = `legal_dong.full_name = '서울특별시 {sigungu} {dong}'` 조회. 실패 시 `pnu=NULL`, 실패 사유 카운트
- 제공 파일은 현행 코드만. 폐지 동명 때문에 조회에 실패한 건수를 리포트에 따로 남기고, 전체 실패율이 0.5% 안이면 폐지 코드는 적재하지 않는다 (docs/03 D3). 아래 폐지 코드 규칙과 `legal_dong.abolished`는 폐지 코드 파일을 나중에 넣을 때를 위해 그대로 둔다
- 같은 이름에 코드가 여러 개일 때 (T-011에서 확정):
  - 현행 코드가 1개면 폐지 코드가 함께 있어도 **현행 코드**를 쓴다. 사용자 주소 검색(§2.2)은 도로명주소 API가 현행 코드를 주므로, 폐지 코드로 만든 PNU는 검색 결과와 맞지 않는다
  - 현행 코드가 없고 폐지 코드만 1개면 폐지 코드로 PNU를 만든다. 실패가 아니며 실패율에 넣지 않는다. 건수는 따로 세어 리포트에 적는다 (`abolished_only`)
  - 현행 코드가 2개 이상이면 PNU를 만들지 않는다. 실패 사유 `ambiguous`
  - 현행 코드가 없고 폐지 코드만 2개 이상이어도 고를 근거가 없으므로 `ambiguous`
- 실패 사유: `regex_mismatch`(정규식 불일치), `dong_not_found`(이름이 `legal_dong`에 없음), `ambiguous`. 뒤 둘이 정의의 "`legal_dong` 조회 실패"다
- `main`·`sub`가 4자리를 넘으면 PNU 19자리에 담을 수 없으므로 `regex_mismatch`로 센다
- `sub`가 없거나 `0`이면 `0000`
- `tail`은 층·호 파싱에 사용

| 입력 | 기대 |
|---|---|
| `서울특별시 광진구 화양동 47-1 ` | 화양동 코드 + `1` + `0047` + `0001` |
| `서울특별시 광진구 광장동 110-0` | 부번 `0000` |
| `서울특별시 광진구 광장동 산 21` | 산 여부 `2`, 본번 `0021` |
| `서울특별시 중구 을지로3가 296-1` | 동 이름 `을지로3가` |
| `서울특별시 종로구 종로1가 24` | 동 이름 `종로1가` |
| `서울특별시 광진구 자양동 227-342 롯데백화점스타시티점 지하1층` | PNU 정상, `tail` = `롯데백화점스타시티점 지하1층` |
| `서울특별시 광진구 구의동 631-1 프라임 상가 1층 124, 134,135` | `tail` = `프라임 상가 1층 124, 134,135` |
| `서울특별시  광진구   군자동 49-19` (공백 여러 개) | 공백 정규화 후 정상 |

> **PNU 생성 실패율** = (지번 정규식 불일치 + `legal_dong` 조회 실패) ÷ 서울 필터를 통과한 전체 기록. 기준 **< 0.5%** (T-011 수용 기준, DV6, Gate 1 공통). 실패 사례 상위 20개를 리포트에 남긴다.

## 4. 호 파서

- `(\d+)\s*호` 모든 매치 → `ho_list`
- 층 바로 뒤 숫자 나열(`1층 124, 134,135`)은 `호` 글자가 없어도 쉼표로 구분된 3~4자리 숫자 목록이면 `ho_list`에 포함
- 정규화: 앞의 0 제거(`0101` → `101`), 중복 제거, 오름차순
- 사례: `2층 206호` → `['206']`, `1층 124, 134,135` → `['124','134','135']`, `가동 101호` → `['101']`(동 구분은 MVP에서 무시), `B101호` → `['101']`

## 5. 행정 일괄 폐업일 탐지 (ADR-020)

```
대상: status='closed' AND closed_on IS NOT NULL
c(j, d) = 관할 j(개방자치단체코드), 날짜 d의 폐업 건수 (식품 3종 합산)
m(j)    = 관할 j에서 폐업이 1건 이상 있었던 날들의 c(j, d) 중앙값
bulk(j, d) = c(j, d) >= 30 AND c(j, d) >= 10 * m(j)
```
- 해당 (j, d)의 기록 전체에 `bulk_closure=true`
- 지표: 탐지 날짜 수, 기록 수를 `data_snapshot.validation`에 기록
- 검증(T-015): W0 방식(서울 전체 하루 100건 이상, 일반음식점)이 일괄 폐업으로 분류한 **기록 44,194건** 중 새 규칙도 `bulk_closure=true`로 표시한 비율 ≥ 95%. 미달 시 임계값 조정 근거를 ADR로 남긴다

## 6. 미갱신 의심 (ADR-023)

같은 층키에서 기록 A(`status='open'`)보다 나중에 개업한 기록 B가 있고, 다음 중 하나면 A에 `stale_suspect=true`
- A와 B의 `ho_list`가 하나 이상 겹침
- A와 B의 면적 차이가 ±1% 이내 (둘 다 면적 있음)

화면: A 옆에 "폐업 신고가 늦어진 것으로 보여요" 배지. 통계 계산에는 사용하지 않음(민감도 분석에만).

## 7. 이력과 통계

### 7.1 층 이력 (화면용)

정렬: `opened_on` 오름차순. 각 항목:
`{record_id, name, biz_category, license_type, opened_on, closed_on, status, tenure_days, ho_list, bulk_closure, stale_suspect}`
- `tenure_days` = (`closed_on` 또는 기준일) − `opened_on`
- 같은 `ho_list` 원소를 공유하는 기록끼리는 화면에서 "같은 호수로 신고된 기록"으로 묶어 색을 맞춘다 (연결선 표시)
- `has_concurrent` = 이력 중 영업 기간이 30일 넘게 겹치는 쌍 존재 → "이 층에는 여러 점포가 함께 있을 수 있어요"
- `record_suppression`에 있는 기록은 제외

**알림(`notices`) 발생 조건**

| 값 | 조건 |
|---|---|
| `multiple_units_possible` | `has_concurrent = true` |
| `bulk_closure_present` | 이력 중 `bulk_closure = true` 기록 1건 이상 |
| `stale_suspect_present` | 이력 중 `stale_suspect = true` 기록 1건 이상 |
| `pre_2005_floor_missing` | 같은 필지에 층 정보 없는 기록 중 `opened_on < 2005-01-01`인 기록 1건 이상 |

### 7.2 과거 폐업 횟수와 기준율

**정의 (method_version `2026.10.1`)**
- 층키 기록 집합 `F(pnu, floor)` — 식품 3종, `floor IS NOT NULL`
- 기록 r의 과거 폐업 횟수: `prior(r) = |{ s ∈ F : s ≠ r, s.status='closed', s.closed_on < r.opened_on }|` (일괄 폐업 기록 포함)
- 코호트: `opened_on ∈ [2005-01-01, 기준일 − 1095일]`, `pnu`·`floor` 있음, `r.bulk_closure = false`
- 결과: `event(r) = r.status='closed' AND r.closed_on − r.opened_on ≤ 1095일`
- 버킷: `0, 1, 2, 3, 4+`
- 범위: 서울 전체(`scope_code='11'`)와 시군구별
- 비율과 Wilson 95% 신뢰구간:
  ```
  p̂ = events/n,  z = 1.96
  center = (p̂ + z²/(2n)) / (1 + z²/n)
  half   = z·sqrt(p̂(1−p̂)/n + z²/(4n²)) / (1 + z²/n)
  ```
- **표시 조건**: 해당 버킷 `n ≥ 200`. 시군구 버킷이 조건을 만족하면 시군구 값을 주로, 서울 값을 보조로 표시. 아니면 서울 값만

**화면의 "이 층의 현재 과거 폐업 횟수"** = `|{ s ∈ F : s.status='closed', s.closed_on ≤ 기준일 }|` → 버킷 매핑

## 8. 호실 연결 연구 트랙 (`location/matching`, 게이트 전 비공개)

### 8.1 문제
같은 층에 점포가 여러 개일 때 어떤 기록들이 같은 호실인지 추정. 정답 라벨은 신고된 호수(노이즈 있음: 같은 호 연속 기록의 28.4%가 30일 넘게 겹침, 27.0%는 면적 차 25% 초과).

### 8.2 기준선 (W0, 서울, 2000년 이후, 층·호·면적 있는 기록)
평가셋: 레코드 54,322 · 층 10,352 · 실제 호실 36,415

| 방법 | 쌍 정밀도 | 쌍 재현율 | F1 |
|---|---|---|---|
| 층 전체를 한 자리로 (전체) | 0.120 | 1.000 | 0.214 |
| 층 전체를 한 자리로 (호실 6개 이하 층) | 0.269 | 1.000 | 0.424 |
| 시간 겹침 금지 + 면적 ±25% 탐욕 연결 (호실 6개 이하 층) | **0.685** | **0.426** | **0.525** |

참고: 같은 호 연속 기록 중 면적이 **완전히 같은** 비율 47.1% → 강한 특징.

### 8.3 접근
1. 라벨 정제: 같은 호인데 30일 넘게 겹치는 쌍은 학습 라벨에서 제외(미갱신 의심)
2. 쌍 분류기: 특징 = 면적 완전 일치, |log 면적비|, 공백 일수, 겹침 일수, 업태 동일, 상호 유사도(자모 단위 Jaccard), 층 내 기록 수, 둘 다 호 정보 보유 여부
3. 클러스터링: 분류기 확률을 비용으로 한 최소 비용 체인(시간 겹침 금지 제약)
4. 분할: **시군구 단위** train 15 / val 5 / test 5 (같은 건물이 학습·평가에 섞이지 않게)
5. 지표: 쌍 정밀도·재현율·F1, B-cubed. 소형 층(≤6호실)과 전체를 따로 보고
