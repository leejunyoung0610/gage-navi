# 02. 설계 결정 기록 (ADR)

형식: **맥락 → 결정 → 결과(감수하는 것)**. 결정을 바꾸려면 기존 ADR을 수정하지 말고 새 ADR을 추가해 "대체함: ADR-xxx"를 적는다.

---

## 판단 신뢰성

### ADR-001 LLM은 추출만, 판단은 결정론적 규칙 엔진
- **맥락**: 정책자금·폐업 지원은 돈이 걸린 판단이다. LLM은 그럴듯한 오답을 낸다.
- **결정**: LLM은 공고 원문 → 규칙 JSON 추출에만 사용한다. 자격·금액·순서·설명은 코드가 계산한다. `rules/extraction` 밖에서 LLM SDK import 금지(import-linter).
- **결과**: 규칙으로 표현 못 하는 조건은 "확인 필요"로 남는다(ADR-003). 표현 불가율을 지표로 추적한다.

### ADR-002 사람 검수 없이 규칙 배포 금지
- **결정**: `rule.status`는 `draft → approved → retired`. 엔진은 `approved`만 로드한다. 승인은 관리자 화면에서만 가능하고 `review_log`에 남는다.
- **결과**: 공고 변경 반영이 사람 검수 속도에 묶인다. 검수 시간을 지표로 줄여나간다.

### ADR-003 3치 판정 (충족 / 불충족 / 확인 필요)
- **결정**: 조건 평가 결과는 `MET | NOT_MET | UNKNOWN`. 입력 누락·원문 모호·표현 불가는 `UNKNOWN`.
- **결과**: 결과가 덜 단정적으로 보인다. 대신 "무엇을 입력하면 판정되는지"를 함께 보여준다.

### ADR-004 모든 판단에 근거와 버전
- **결정**: 판단 결과마다 근거 문장(문서 ID, 위치), 규칙 버전, 엔진 버전, 기준일을 붙인다. 자리 통계에는 데이터 스냅샷 날짜와 표본 수를 붙인다.
- **결과**: 응답이 커진다. 화면에서는 "근거" 버튼 뒤에 접어서 보여준다.

### ADR-005 근거 없는 예측 숫자 금지
- **맥락**: W0 분석에서 과거 폐업 이력은 통계적으로 유의했지만(OR 1.075/회, p<1e-37), 개별 예측력 증가는 AUC +0.002에 불과했다.
- **결정**: 선정 확률, 자리 위험 점수, 성공 확률을 만들지 않는다. "비슷한 경우들의 실제 결과(기준율)"만 신뢰구간·표본 수와 함께 보여준다.
- **결과**: "점수"를 원하는 사용자는 실망할 수 있다. 방법론 페이지에서 이유를 공개한다.

### ADR-006 입력값은 원본 단위로 보존, 계산 시 변환
- **결정**: 면적은 `{value, unit: m2|pyeong, basis: exclusive|contract|unknown}`로 저장한다. 각 규칙이 요구하는 단위로 계산 시점에 변환한다. 1평 = 400/121 ㎡(≈3.3058)로 고정하고 반올림은 규칙에 명시된 방식만 쓴다.
- **결과**: 계산 함수가 단위 인자를 받아야 한다.

### ADR-007 기준일(as_of) 명시
- **결정**: 모든 평가 API는 `as_of`(기본: 서버 오늘, Asia/Seoul)를 받는다. 테스트는 고정 기준일을 쓴다.
- **결과**: 시간에 따라 바뀌는 결과도 재현 가능하다.

### ADR-008 충돌 조건은 한쪽만 선언해도 양방향 적용
- **결정**: 공고 A가 B와의 중복을 금지하면, B 공고에 언급이 없어도 A–B 충돌로 처리한다. 범위(`apply`/`benefit`)가 불명확하면 `apply`(더 보수적)로 처리하고 "확인 필요" 표시.
- **결과**: 실제보다 보수적인 추천이 나올 수 있다.

### ADR-009 자격과 접수 상태는 별개 축
- **결정**: 자격(ADR-003)과 접수 상태(`UPCOMING|OPEN|CLOSED`, `budget_limited`)를 따로 판정한다. 추천 대상 = 자격 ∈ {MET, UNKNOWN} ∧ 접수 상태 ∈ {UPCOMING, OPEN}.

### ADR-010 사용자에게 보이는 설명 문장은 템플릿 생성
- **결정**: 이유 문장은 결정 조건 ID → 한국어 템플릿으로 생성한다. LLM으로 생성하지 않는다.

## 제품·범위

### ADR-011 웹 우선 + PWA, 네이티브 앱은 조건부
- **맥락**: 자리 조회는 1~수회성이라 설치 장벽이 치명적이다. 자리 페이지 검색 노출이 핵심 유입 채널이다. 포트폴리오 평가자는 링크로만 본다. 애플 App Store 심사 지침(5.1.1(ix))은 금융 등 규제 분야 앱을 개인이 아닌 해당 서비스를 제공하는 법인이 제출하도록 요구하므로 정책자금 기능이 심사 리스크가 될 수 있다.
- **결정**: Next.js 모바일 우선 반응형 + PWA(홈 화면 설치). 네이티브 앱(Expo 래핑)은 다음 조건을 모두 만족할 때 새 ADR로 검토: (1) 알림 기능 사전 신청자 수가 월 순방문자의 10% 이상, (2) 정책자금 모듈 Gate 2 통과, (3) 법인 또는 심사 리스크 검토 완료.
- **결과**: iOS 웹 푸시는 홈 화면 추가 사용자만 가능하다. 알림은 MVP 비목표.

### ADR-012 프론트엔드는 Next.js (SPA 아님)
- **결정**: 자리 페이지(`/place/...`)는 서버 렌더링 + ISR로 생성해 검색 색인 가능하게 한다. 마법사 화면은 클라이언트 컴포넌트.
- **결과**: 기존 React SPA 경험에서 App Router 학습 비용이 든다.

### ADR-013 백엔드는 Python FastAPI 단일 서비스
- **결정**: 데이터 처리·통계·규칙 엔진·API를 한 Python 서비스에 둔다. 모듈 경계는 패키지와 import-linter로 강제한다.
- **결과**: 마이크로서비스의 독립 배포 이점은 포기한다(1인 개발에 불필요).

### ADR-014 사용자 데이터를 서버에 저장하지 않음
- **결정**: 사업장 프로필(매출, 신용 구간, 부채 등 민감 정보 포함)은 브라우저 `localStorage`에만 저장한다. 서버는 요청 처리 후 폐기하고 로그에 본문을 남기지 않는다. 로그인 없음.
- **결과**: 기기 간 동기화·알림이 불가하다. 사용자에게 "이 기기에만 저장돼요"를 고지하고 삭제 버튼을 제공한다.

### ADR-015 자리 이력 표시 단위는 "층", 호실은 일치할 때만
- **맥락**: W0 기준선에서 같은 층 안 호실을 시간 겹침+면적으로 추정 연결하면 소형 층 기준 쌍 정밀도 0.685, 재현율 0.426이었다. 정답 라벨(신고된 호수)도 같은 호 연속 기록의 28%가 30일 넘게 동시 영업으로 남아 있어 노이즈가 크다.
- **결정**: 화면은 층 단위 이력을 기본으로 보여주고, 신고된 호수가 같은 기록만 "같은 호수로 신고된 기록"으로 묶는다. 추정 연결은 docs/00 §5.3 게이트 통과 전까지 표시하지 않는다.
- **결과**: 큰 상가 층에서는 이력이 여러 호실의 합으로 보인다. 화면에 "이 층에는 여러 점포가 함께 있을 수 있어요"를 표시한다.

### ADR-016 기준율 통계 키는 "층키"
- **결정**: 과거 폐업 횟수는 W0에서 검증된 층키(PNU + 층) 기준으로 센다. 호실 단위 재검증은 게이트 이후 별도 ADR.

### ADR-017 정책자금 기본 목적함수는 "필요 금액을 최소 비용·최대 확실성으로"
- **맥락**: 브로커는 수수료가 승인액에 비례해 한도 최대화를 판다. 사장님에게 필요한 건 필요한 만큼의 자금이다.
- **결정**: 기본 계획 = 필요 금액 충족 + 금리(알 수 있을 때) 최소 + 확실성 최대. 한도 최대안은 "참고안"으로만, 부채 증가 경고와 함께 표시.

### ADR-018 MVP 지역은 서울 단일
- **결정**: 3개 모듈 모두 서울특별시로 한정한다. 데이터 검증·규칙 라벨링 범위를 맞추기 위함.

### ADR-019 하나의 서비스, 단계적 공개
- **결정**: 한 도메인·한 브랜드에 3개 모듈. 모듈별 게이트(docs/50 §7) 통과 시 공개, 미통과 모듈은 베타 배너 + 비공개 링크. 모듈 간 코드 격리(ADR-013).

## 데이터·구현

### ADR-020 폐업 처리 급증일 (옛 이름: 행정 일괄 폐업일)
- **맥락**: 서울 데이터에 하루 100건 이상 폐업 처리된 날이 238일, 44,194건 있다(W0, 일반음식점). W0는 이를 "실제 폐업 시점이 아닌 행정 정리"로 보고 통계에서 뺐다.
- **결정 (2026-10-13 개정, T-015)**
  - 탐지 규칙(docs/10 §5: 관할별 하루 30건 이상이고 관할 중앙값의 10배 이상)은 **"폐업 처리 급증일"** 탐지로 유지한다. "그날 그 관할에서 평소보다 훨씬 많은 폐업이 처리됐다"는 것은 정의상 사실이라 검증이 필요 없다. 컬럼·필드 이름 `bulk_closure`는 그대로 둔다
  - **"행정 일괄 정리"라는 해석은 지금 데이터로 검증할 수 없다.** 화면은 해석이 아니라 사실만 말한다: 배지 "폐업 처리 몰린 날", 설명 "이날 {관할 이름}에서 평소보다 훨씬 많은 폐업이 한꺼번에 처리됐어요({n}건). 실제로 문을 닫은 날은 더 이를 수 있어요." (docs/40 §4.4). "행정 일괄 정리"라는 표현은 화면에 쓰지 않는다
  - 통계에서 어느 정의로 제외할지는 하나로 정하지 않는다. T-019가 **제외 없음 / 새 규칙(`bulk_closure`) / W0 정의(일반음식점, 서울 전체 하루 100건 이상)** 세 가지로 기준율을 계산해, 결론(과거 폐업이 많을수록 3년 내 폐업률이 높다)이 유지되는지 모형 카드에 보여준다. `method_version='w0'` 재현 모드는 W0 정의를 그대로 쓴다
  - **통계의 기본 설정은 새 규칙(`bulk_closure`)으로 제외 (2026-10-13, T-019 시작 전 사용자 결정)**: 급증일에 폐업한 기록은 코호트에서 빼고 과거 폐업 횟수에도 세지 않는다. 제외 없음·W0 정의는 민감도로 함께 계산한다. 결론이 유지되는지의 판정 기준(4+ 버킷과 0 버킷의 Wilson 구간이 겹치지 않음, 로지스틱 OR 하한 > 1)은 결과를 보기 전에 docs/10 §7.3에 적었다. 한 설정에서라도 깨지면 화면 카드를 확정하지 않고 멈춘다
  - "서울 전체 하루 100건"을 탐지 규칙에 OR 조건으로 더하는 안은 기각 — 어느 관할도 몰리지 않은 연말·분기 말의 폐업에도 배지가 붙는다
- **결과**: 민감도 분석(제외 대신 중도절단 처리) 결과를 방법론 페이지에 함께 싣는다.
- **측정 기록 (2026-10-13, 식품 3종 원천 704,141행, `reports/bulk_closure.md`)** — 검증 실패도 결과로 남긴다
  - *처음 기준과 그 실수*: "W0 방식이 일괄 폐업으로 분류한 44,194건 중 새 규칙도 표시한 비율 ≥ 95%"였다. 측정값은 **70.24%**(31,040건)이고 임계값을 낮춰도 닿지 않는다(최소 10건·중앙값 5배에서 74.15%, 표시 기록은 45,850 → 72,004). 차이는 **W0 정의가 넓어서** 생긴다. W0는 "서울 전체 하루 100건 이상인 날"의 일반음식점 폐업 전부를 보고, 새 규칙은 관할 하나가 평소의 10배 이상 몰린 (관할, 날짜)만 본다
  - 놓친 13,154건의 구성: **9,849건**은 탐지된 관할이 하나 이상 있는 W0 일괄 폐업일 208일에 다른 관할에서 폐업한 기록, **3,305건**은 어느 관할도 탐지되지 않았는데 서울 전체가 100건을 넘은 30일(12-30·12-31·03-31·09-30·04-01 같은 연말·분기 말·월초. 기록이 많은 10일의 관할별 건수 최댓값은 12~28건)의 기록. 반대로 새 규칙만 표시한 기록이 14,810건 있다
  - **95% 기준은 설계 실수였다.** W0의 "하루 100건"은 거친 대리 지표인데, 더 좁은 규칙에게 그 지표와의 일치를 요구했다
  - *타당성 측정*: 같은 층키(PNU+층)에서 같은 호(`ho_list` 겹침) 또는 면적 ±1%인 다른 기록이, 이 기록보다 나중에 그리고 이 기록의 공식 폐업일 전에 이미 개업한 비율(docs/10 §6 미갱신 의심과 같은 조건). 기대는 "① 새 규칙이 표시한 폐업이 ② 표시 안 된 일반 폐업보다 뚜렷하게 높고, ③ W0만 일괄로 본 30일의 폐업은 ②와 비슷하다"였다

    | 묶음 | 폐업 기록 | 분모(층키·개업일·폐업일 있음) | 비율 | 같은 호 | 면적 ±1% |
    |---|---|---|---|---|---|
    | ① 새 규칙이 표시한 폐업 | 45,850 | 13,146 (29%) | **10.12%** | 2.31% | 8.88% |
    | ② 표시 안 된 일반 폐업 | 483,875 | 230,945 (48%) | **9.07%** | 1.94% | 8.05% |
    | ③ W0만 일괄로 본 30일의 폐업 | 3,305 | 1,654 (50%) | **13.66%** | 2.66% | 12.39% |

  - **기대와 다르다.** ①은 ②보다 약 1%p 높을 뿐이고(폐업 연도 구간별로도 2000년 이후 0.9~1.2%p), ③은 ②와 비슷하지 않고 가장 높다(2020년 이후 구간 안에서도 15.09% 대 11.91%). 이 측정으로는 ①이 행정 정리라는 것도, ③이 평소 폐업이라는 것도 뒷받침되지 않는다
  - 이 지표의 한계: ①의 **층키 커버리지가 29%**(1999년 이전 12,469건 중 분모 173건)라 ①의 대부분을 보지 못한다. ②의 기준선 9%는 대부분 면적 ±1%에서 나온다 — 한 층에 여러 점포가 있고 면적이 비슷하면 신고 지연과 상관없이 잡힌다. 식품 3종 밖의 업종이 뒤에 들어온 경우는 보이지 않는다
  - 원천에 처리 사유가 없다: `상세영업상태명`은 세 파일 모두 `영업`(코드 01)·`폐업`(코드 02) 두 값뿐이다(일반음식점 120,047 / 419,542, 휴게음식점 36,910 / 110,721, 제과점영업 4,274 / 12,647). 직권 말소 같은 구분으로 가를 수 없다

### ADR-021 금액은 원 단위 정수
- **결정**: 모든 금액은 `int`(원). 부동소수 금지. 비율 계산 후 원 미만은 규칙에 명시된 방식, 미명시 시 내림.

### ADR-022 최적화 알고리즘
- **결정**: 후보 사업 ≤ 8개면 순서까지 고려한 분기 한정 DFS로 정확해 계산(길이 0~8의 순서 있는 부분열 109,601개, 가지치기 전 기준). 초과 시 CP-SAT(순서 효과 근사)로 전환하는 인터페이스를 고정해 둔다. MVP에서 CP-SAT는 구현하지 않는다(후보 수 초과 시 계획 생략 + 경고, 사업별 판정은 반환).

### ADR-023 미갱신 의심 기록 플래그
- **맥락**: 폐업 신고 없이 "영업 중"으로 남는 기록이 있어, 같은 자리에 새 업소가 개업한 뒤에도 이전 기록이 영업 중으로 겹친다.
- **결정 (2026-10-13 개정, T-017)**: 같은 층키에서 이후 개업한 다른 기록이 있는데 이전 기록이 여전히 영업 중이면 표시한다. 근거를 나눠 저장한다 — 같은 호수면 `stale_suspect`, 같은 면적(±1%)이면 `stale_area_match`. 통계에서는 W0 정의를 유지(플래그는 민감도 분석에만 사용). 규칙은 docs/10 §6
  - **화면에는 같은 호 근거만 낸다.** 면적 ±1% 겹침은 우연이 많다(T-015 측정: 같은 조건이 일반 폐업에서도 8.05%, ADR-020). 면적 근거는 통계 민감도 분석에만 쓴다
  - **같은 가게로 보이는 쌍은 뺀다.** 식품 3종을 합쳤기 때문에 한 가게가 같은 호에 종류가 다른 인허가 기록을 함께 가질 수 있어, 멀쩡한 가게가 신고 지연으로 잡힌다. 사업장명이 같거나 한쪽이 다른 쪽을 포함하는 쌍을 뺀다
  - **여러 사업자가 함께 쓰는 호는 같은 호 근거에서 뺀다.** 한 층키에서 같은 호 번호를 가진 영업 중 기록이 3건 이상이면 공유 공간(공유주방 등)으로 본다. 처음 구현에서는 같은 호 근거 2,380건 중 430건(18%)이 기록 10건 이상이 몰린 층키 27곳에서 나왔다 — 서로 다른 가게가 동시에 영업하는 곳이다. 화면에 보이는 부정적인 표시라 **틀린 배지보다 놓친 배지가 낫다**는 기준으로 정했다. 결과: 2,380건 중 530건(22.27%)이 빠져 1,850건. 10건 이상 몰린 층키는 27곳에서 7곳(89건)으로 줄었고, 남은 7곳은 여러 호에 흩어진 큰 층이다(`reports/stale_suspect.md`)
  - 화면 문구는 사실과 가능성만 말한다: "같은 호수로 나중에 다른 가게가 영업 신고를 했어요. 이 가게의 폐업 신고가 늦어졌을 수 있어요." (처음 문구 "폐업 신고가 늦어진 것으로 보여요"는 확인하지 못한 해석이라 바꿨다, docs/40 §6)

### ADR-024 문서 변환 방법 (형식별 go/no-go)
- **맥락**: T-051S에서 실제 공고 7건(PDF 4, HWP 3)을 변환해 본문 누락과 표 보존을 쟀다. 수치와 방법은 `reports/conversion_spike.md`. HWPX 표본은 구하지 못했다.
- **결정**:
  - **PDF — go.** pdfplumber. 표 영역은 셀 단위로 뽑아 `| 셀 | 셀 |` 행으로, 표 밖은 페이지별 줄로 쓴다. 셀 추출이 표 영역의 글자를 잃는 표(셀 글자 수 < 영역 글자 수의 98%)는 줄 텍스트로 대체하고 표시한다. 글자가 없는 페이지가 있으면 `failed` → 수동 텍스트.
  - **HWP — go.** olefile로 본문 스트림의 레코드 트리를 직접 읽는다(문단은 한 줄, 표는 `| 셀 | 셀 |` 행). 암호·배포용 문서와 5.x가 아닌 파일은 `failed` → 수동 텍스트.
  - **HWP `hwp5txt` — no-go.** 표를 `<표>` 한 줄로 바꾸고 내용을 버려 본문의 22~33%만 나온다.
  - **pyhwp는 의존성으로 넣지 않는다.** AGPLv3+ 라이선스, 선언되지 않은 `six` 의존, 베타 버전. 스파이크에서 대조용으로만 썼고 직접 파싱과 결과가 일치했다.
  - **HWPX — 판정 보류.** 표본이 없어 수동 텍스트 경로로 둔다. 표본이 생기면 같은 지표로 재판정하고 이 ADR을 고친다.
- **결과**: docs/20 §10.2, docs/01 §2의 변환 방법을 이 결정에 맞춘다. T-051에서 `pdfplumber`, `olefile`을 추가한다. 줄로 대체된 PDF 표의 인용은 옆 칸 글자가 섞일 수 있으므로 검수자가 원문과 직접 대조한다.

### ADR-025 인허가 데이터 갱신은 월 1회 전체 적재
- **맥락**: 설계는 조회 API(D2)로 일 1회 증분 수집 + 월 1회 전체 재적재였다. T-010에서 세 파일 전체 적재를 재 보니 합계 17.7초였다(일반음식점 539,589행 12.5초, 휴게음식점 147,631행 4.2초, 제과점영업 16,921행 0.4초, 로컬).
- **결정**: 증분 수집을 만들지 않는다. 갱신은 **월 1회 전체 파일 적재**(`jobs.ingest_licenses --mode full`)로 한다. 파일은 당분간 사람이 월 1회 포털에서 내려받아 `data/raw/<다운로드일>/`에 넣는다(🧑).
- **근거**: (1) 전체 적재가 18초 안쪽이라 증분으로 아낄 시간이 없다. (2) 스냅샷 단위라 "어느 파일로 계산했는가"를 그대로 재현할 수 있다. (3) 증분은 삭제·변경된 기록을 처리하는 복잡도만 늘린다.
- **결과**: `--mode incremental`은 없다. docs/03 D2·§5를 이 결정에 맞춘다. 조회 API(15154916 등)의 파라미터·응답 필드는 확인하지 않았다. 공공데이터포털 키를 받는 T-050 때 다시 볼 수 있다.

### ADR-026 인허가 좌표의 원천 좌표계는 EPSG:5174
- **맥락**: 인허가 파일의 `좌표정보(X)`, `좌표정보(Y)`에는 좌표계 표기가 없다. 후보는 EPSG 2097, 5174, 5181, 5186이었다(T-014). 후보별 변환 값과 표본은 `reports/crs_candidates.md`(`jobs.crs_candidates`, 2026-10 세 파일, 좌표가 있고 지번주소가 서울인 663,782행).
- **결정**: 원천 좌표계는 **EPSG:5174**(Korean 1985 / Modified Central Belt). `app/location/normalize/coords.py`의 `to_wgs84(x, y) -> (lat, lng)`가 pyproj로 EPSG:4326으로 바꾼다.
- **근거**:
  - **5186 탈락 (값 범위)**: 5186으로 바꾸면 663,782행 전부가 위도 36.52657~36.78834에 놓인다. 나머지 세 후보는 37.43~37.69다. 5186의 Y 가산값은 600,000m, 나머지는 500,000m이고 원천 Y는 436,477~465,525다. 지도 링크 확인은 하지 않았다.
